# MPC 솔버 선택·튜닝 근거 — 측정 로그

> `mpc-solver.md` 에서 분리했다(2026-07-30, 파일 크기 때문에 분리, 같은 `paths`
> 트리거라 함께 로드된다). 여기는 **왜 이렇게 정했는지의 측정 근거**다. 현재
> 정식화 자체는 `mpc-solver.md` 를 봐라.

## 왜 IPOPT 인가

**정직한 답: CasADi 에 번들되어 있고 Mehrez 워크숍 계보를 따랐기 때문이다.**
제어이론적 근거로 고른 것이 아니다. 이 절은 그 사실과, 실제로 재본 대안들을 남긴다.

정당한 근거가 있는 부분은 **"NLP 솔버여야 한다"까지**다 — GP 평균이 비선형 커널이라
결합 모델이 비선형이므로 NMPC 다(`mpc-solver.md`「GP 결합 시」). 그것이 `osqp`/
`qpOASES` 같은 **QP** 솔버를 금지하는 이유이고, "하필 IPOPT"를 정당화하지는 않는다.

**IPOPT 는 실시간 MPC 용 솔버가 아니다.** 범용 내부점법이고, 내부점법의 알려진 약점이
warm start 다. 실시간 NMPC 는 보통 SQP + RTI(스텝당 1반복) 나 active-set QP 를 쓴다.

### 재본 대안 — `fatrop` 은 이 정식화에서 쓸 수 없다 (측정됨)

CasADi 3.7.2 에는 `ipopt` 외에 `fatrop`, `sqpmethod`, `blocksqp`, `qrsqp`, `bonmin`,
`alpaqa` 가 이미 들어 있다(새 의존성 불필요). `fatrop` 은 OCP 의 단계별 구조를 이용하는
내부점법이라 후보였으나, 재보니 못 쓴다.

| 설정 (loop10, 25 s 프로브, N=50) | solve mean | p95 | RMS e_y | 수렴 실패 |
|---|---|---|---|---|
| ipopt 현재 | 12.06 ms | 13.97 | 1.031e-2 | 0 |
| ipopt + warm start | **7.70 ms** | 9.59 | 1.031e-2 | 0 |
| fatrop 기본 | **97.92 ms** | 106.60 | 1.031e-2 | 0 |
| fatrop + `structure_detection: auto` | 70.67 ms | 75.00 | **3.04e+2 발산** | **1250/1250** |

`fatrop` 기본은 답은 맞게 내지만 **10배 느리다**(내부 타이밍: 함수평가 11 ms, 솔버 자체
86 ms — 오버헤드가 아니라 솔버가 느리다). 구조탐지를 켜면 전 스텝 수렴 실패한다.

**원인 추정(미검증)**: `mpc_base.py` 가 `X = opti.variable(4, N+1)` 다음
`U = opti.variable(1, N)` 로 **상태 전체 → 입력 전체** 순서로 변수를 만든다. `fatrop` 이
단계별 구조를 잡으려면 `x0,u0,x1,u1,...` 로 **스테이지별 교차 배치**가 필요하다. 지금
배치로는 구조탐지가 실패해 일반 경로로 떨어지는 것으로 보인다. 확인하려면 변수 순서를
바꿔 다시 재야 한다. **재보지 않고 fatrop 이 빠를 것이라고 적지 마라.**

`acados`(RTI + condensing + codegen)는 이 크기를 보통 1 ms 안에 풀지만
**`requirements.txt` 에 없는 의존성**이다. `python-conventions.md` 「의존성」이 먼저
물어보라고 못박아 뒀고, 솔버 교체는 기존 결과와의 비교 가능성을 깬다. 도입하려면
사용자 승인 + 전 시나리오 재측정이 전제다.

## 지평을 늘릴 때 — 먼저 warm start 를 확인하라

`N` 을 키워 실시간성이 깨졌다면 **정식화를 손대기 전에 솔버 옵션을 먼저 보라.**
move blocking(제어지평 < 예측지평) 같은 정식화 변경은 아래 이유로 여기서는 효과가 적다.

**multiple shooting 에서는 상태가 결정변수의 대부분이다.**

```
N_p=50            X = 4x51 = 204,  U = 50   -> 254 vars
N_p=50, N_c=15    X = 4x51 = 204,  U = 15   -> 219 vars   (고작 -14%)
```

측정된 solve 비용은 변수 수에 대략 선형이므로 균등 move blocking 의 기대 절감은
1~1.5 ms 다. warm start 활성화가 2.5 ms 를 아꼈으므로 **비교가 안 된다.** blocking 이
크게 남으려면 condensing(single shooting)으로 `X` 를 소거해야 하는데, 그건 정식화
재작성이고 조건수가 나빠진다.

**게다가 균등 blocking 은 이 문제에서 「틀린 0」과 같은 부류의 오류를 만든다.** 꼬리
스텝의 `delta` 를 하나로 묶으면 옵티마이저에게 "그 구간 내내 한 조향값으로 충분하다"고
말하는 셈인데, 정상선회에 필요한 `delta` 는 `kappa` 를 따라간다. `N_p=50` 의 꼬리 35
스텝은 `vx=25` 에서 17.5 m 이고 loop10 의 클로소이드 길이가 20 m 이므로 **곡률 전이를
그대로 걸친다.** 꼬리 비용에 없앨 수 없는 성분이 생기고 그 기울기가 지금 적용할 입력을
오염시킨다.

굳이 blocking 을 쓸 거면 **비균등 블록**이어야 한다 — 실제 적용되는 입력은 `k=0` 이므로
앞은 촘촘히, 꼬리는 굵게.

### 측정 — 꼬리 동결(균등)이 굵은 블록보다 **느리고 추종도 나쁘다**

loop10 전체 랩, 비선형 플랜트, warm start 켠 상태:

| 설정 | vars | solve mean | p95 | dt 초과 | RMS `e_y` | 실패 |
|---|---|---|---|---|---|---|
| N=50 블로킹 없음 | 254 | 9.19 ms | 12.77 | 0.6% | 7.6630e-3 | 0 |
| **N=50 자유20 + 꼬리 굵은블록** `[1]x20+[4]x5+[10]x1` | 230 | **7.77 ms** | **9.69** | **0.1%** | 7.6641e-3 | 0 |
| N=50 자유20 + **꼬리 동결** `[1]x20+[30]x1` | 225 | 9.17 ms | 15.15 | 1.9% | **7.8110e-3** | 0 |
| N=60 블로킹 없음 | 304 | 10.61 ms | 15.03 | 0.8% | 7.4814e-3 | 0 |

- **굵은 블록은 사실상 공짜다**: 블로킹 없음 대비 solve mean −15%, p95 −24%, RMS `e_y`
  차이는 **+0.014%**(7.6630e-3 -> 7.6641e-3).
- **꼬리 동결은 변수가 더 적은데도(225 < 230) 더 느리다**(mean 9.17 vs 7.77, p95 15.15
  vs 9.69) **그리고 추종도 1.9% 나쁘다**. 변수 수가 아니라 **문제가 어려워진 것**이다 —
  달성 불가능한 꼬리를 강요하면 옵티마이저가 그 타협을 찾느라 더 고생한다. 위에서 예측한
  「틀린 0」과 같은 부류의 오류가 측정으로 확인된 셈이다.

**지평을 늘려도 추종이 좋아진다는 보장은 없다.** 세 경로에서 전부 같은 방향이었다:
`N=30 -> 60` 에서 RMS `e_y` 가 ay4 +3.1%, racetrack +2.2%, loop10 +10.6% **악화**.
IPOPT 반복수는 네 경우 모두 p95 = 5 로 같았으므로 반복이 늘어난 것이 아니라 NLP 크기가
2배라 반복당 비용이 2배다. 지평을 키우는 근거는 추종오차가 아니라 다른 데(제약 예견,
안정성 여유)에서 와야 한다.

## 솔버 운영 — warm start 측정

측정 (loop10 전체 랩, 비선형 플랜트, `mpc-solver.md`「솔버 운영」의 4옵션 켬/끔):

| | solve mean | p95 | max | dt 초과 | IPOPT iter | RMS e_y |
|---|---|---|---|---|---|---|
| N=50 끄면 | 11.34 ms | 13.63 | 79.0 | 0.1% | 4.5 | 7.6630e-3 |
| N=50 켜면 | **8.79 ms** | 14.22 | 62.2 | 0.1% | **2.8** | 7.6630e-3 |
| N=60 끄면 | 19.13 ms | 25.56 | 112.8 | **35.3%** | 5 | 7.4814e-3 |
| N=60 켜면 | **10.05 ms** | 15.16 | 78.4 | 0.5% | **2.8** | 7.4814e-3 |

반복수 -40%, **RMS `e_y` 는 소수 5자리까지 동일**(정확도를 팔아 속도를 산 것이 아니다),
수렴 실패 0. 이 덕분에 `N=50~60` 이 실시간 안에 들어온다.

주의 두 가지 — ① warm start 된 내부점법은 active set 이 급변할 때(조향 rate 한계 접촉
등) 덜 강건할 수 있다. 위 측정에서는 실패 0 이고 max solve 도 안 튀었지만
`converged`·fallback 경로를 계속 지켜봐라. ② 위 표에서 N=50 끄면(11.34) 대 N=60
끄면(19.13) 의 차이는 변수 수 증가(1.20배)로 설명되지 않는다. 이 머신의 런 간 변동이
섞여 있으니 **개별 수치를 과신하지 마라.** 견고한 것은 반복수 4.5~5 -> 2.8 이라는
메커니즘 수준 결과다.
