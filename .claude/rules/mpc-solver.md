# MPC 정식화·솔버 룰

## 정식화 (multiple shooting + IPOPT)

- 결정변수: `X (4 x (N+1))`, `U (1 x n_blk)`
  - `n_blk` = 입력 블록 수. `configs/mpc/*.yaml` 의 `u_blocks` 가 비면 `n_blk = N`
    (전 스텝 자유 입력)이고, 그때 정식화는 블로킹 도입 이전과 **정확히 같다.**
    블로킹의 근거·주의는 아래 「지평을 늘릴 때」 참조.
- 파라미터 `P`: `[x0(4), vx_preview(N), kappa_preview(N), u_prev(1)]`
  - **GP 케이스는 여기에 GP 블록을 이어 붙인다** (아래 「GP 결합 시」 참조).
    명목 케이스와 GP 케이스는 `P` 레이아웃이 다르다. 레이아웃 정의는 한 곳에
    두고(예: `P_layout` 헬퍼) 인덱스를 손으로 세지 마라.
- 동역학 등식 제약: `X[:,k+1] = rk4_step(...)`, 각 스텝의 `vx`, `kappa`는 `P`에서 꺼낸다
  (GP 케이스에서는 여기에 GP 보정항이 더해진다)

비용:
```
sum_k [ W_ey*e_y^2 + W_epsi*e_psi^2
        + W_vy*v_y^2 + W_gamma*(gamma - vx*kappa)^2   # gamma 만 참조 상대
        + R_delta*delta^2 + R_ddelta*(delta_k - delta_{k-1})^2 ]
+ 종단항 (e_y, e_psi)
```

제약:
```
|delta| <= delta_max
|delta_k - delta_{k-1}| <= delta_rate_max * dt      # k=0 에는 P의 u_prev 사용
```
상태 제약은 지금 넣지 않는다. 추가하려면 먼저 물어라.

**모든 가중치는 `configs/mpc/*.yaml`에서 읽는다. 하드코딩 금지.**

## 참조 상태·피드포워드를 별도로 계산하지 마라 — `gamma` 한 채널만 예외

`x_ref`, `u_ref`를 명시적으로 만들지 않는다. `kappa` 프리뷰가 지평에 채워지면
MPC가 필요한 요레이트를 스스로 만든다. 비용은 `e_y`, `e_psi`를 0으로 보내고
`delta`와 그 변화율을 벌주는 것으로 충분하다.

Mehrez 워크숍의 multiple shooting 골격을 따르되 **이 점이 다르다.**
워크숍 코드를 그대로 옮기면서 `u_ref` 항을 되살리지 마라.

### 예외 — `W_gamma` 는 `(gamma - vx*kappa)^2` (2026-07-27 사용자 확정)

위 원칙에는 구멍이 있었다. 곡선에서 **완벽추종에 필요한 값이 0 이 아닌** 양을
절대값으로 벌주면, 목적함수가 동역학 등식제약과 반대 방향을 지시한다.
`gamma` 가 그 대표 사례다 (`kappa=0.02, vx=14.14` 에서 필요 `gamma_ss = 0.283 rad/s`).

**측정 근거** (ay4, `plant=linear` 로 모델오차를 0 으로 만든 뒤):
`W_gamma*gamma^2` 는 완벽추종 시 잔여 스테이지 비용의 65.8% 를 차지했고,
일정곡률 정상편차 `e_y` 를 3.35e-3 m 만들었다 (이 항만 끄면 6.87e-4 로 감소).

**이 예외가 `gamma` 에만 허용되는 이유:**

| 채널 | 참조 | 비선형 플랜트 대비 참조 오차 | 판정 |
|---|---|---|---|
| `gamma` | `vx*kappa` — **순수 기구학** | **0.02%** | 예외 허용 |
| `delta` | `kappa*(L + K_us*vx^2)` — `Cf,Cr,m` 의존 | +2.74% | 불허 |
| `v_y` | 선형 정상상태해 — `Cf,Cr,m,Iz` 의존 | **−206.6%** | 불허 |

`gamma_ref = vx*kappa` 는 오차 기구학 `e_psi_dot = gamma - vx*kappa` 그 자체이므로
**차량 파라미터가 하나도 들어가지 않는다.** 따라서 선형모델의 오차를 목적함수에
두 번째 경로로 들여오지 않는다 (CLAUDE.md 「잔차의 출처를 타이어 비선형성 하나로
통제」 유지).

`delta`, `v_y` 의 참조는 GP 가 학습하기로 되어 있는 바로 그 선형모델에서 나온다.
이들을 참조 상대로 바꾸면 실험 설계가 깨진다. **확장하지 마라.**

구현: `p_vx[k] * p_kappa[k]` — 이미 `P` 에 있는 프리뷰를 쓰므로 새 파라미터도
NLP 재빌드도 없다.

## 크기 페널티를 쓸 수 있는 양 — 판정 기준 (2026-07-27 확정)

정상선회에서 차량은 힘·모멘트 평형에 있다. 경로 `(kappa, vx)` 가 평형점을 유일하게
결정하므로 `gamma`, `v_y`, `delta` 는 **경로가 정하는 값이지 컨트롤러가 고를 값이 아니다.**
물리적으로 0 이 정답인 양은 두 종류뿐이다:

1. **추종오차** `e_y`, `e_psi` — "경로 위에 있다"의 정의상 0
2. **시간미분** — "정상상태"의 정의상 0

이 둘 중 어느 쪽도 아닌 양에 `x^2` 를 걸면, 추종 문제에 **레귤레이션 목적(상태를
원점으로)** 을 섞는 것이다. 원점이 목표가 아니므로 이건 튜닝 문제가 아니라 범주 오류다.

따라서 어떤 항의 0 이 틀렸다고 판명되면 대응은 두 가지뿐이다:

| 상황 | 대응 | 적용 사례 |
|---|---|---|
| 믿을 만한 참조가 있다 | 참조 상대로 바꾼다 | `gamma` (참조 오차 0.02%) |
| 믿을 만한 참조가 없다 | **항을 없앤다** | `v_y` (−206.6%), `delta` (+2.74%) |

**가중치만 줄이는 것은 답이 아니다.** 틀린 0 을 유지한 채 "덜 틀리게" 하는 것일 뿐,
편차를 없애지 못하고 근거도 없다.

`W_vy = 0`, `R_delta = 0` 으로 확정했다. 이 결정으로 물리적 안전장치가 사라지지
않는다는 것을 세 시나리오에서 확인했다:

| 시나리오 | RMS `e_y` | max\|α_f\| | max\|α_r\| | rate 포화 |
|---|---|---|---|---|
| ay4 | 1.068e-2 → **8.580e-3** | 3.680° → **3.424°** | 3.134° → **3.089°** | 18.0% → **13.5%** |
| ay6 | 2.945e-2 → **2.473e-2** | 6.858° → **6.413°** | 5.949° → **5.755°** | 23.3% → **16.2%** |
| dlc | 1.092e-2 → **9.232e-3** | 4.243° → **4.143°** | 2.979° → 3.077° | 55.7% → **48.8%** |

추종·전륜슬립·조향포화가 **전부 동시에** 좋아진다. 애초에 이 항들이 안전성이나
평활도를 사주고 있지 않았다는 뜻이다. 각 물리적 관심사는 이미 옳은 구조가 맡고 있다:

- 전륜 포화 → 하드제약 `|delta| <= delta_max`
- 횡방향 안정성 → `A_lat` Hurwitz (언더스티어 `K_us>0` 이면 전 `vx` 보장, vehicle-model.md)
- 액추에이터 평활 → `R_ddelta` (변화율 항이라 정상상태에서 0, 구조가 옳다)

`W_vy`, `R_delta` 를 "작은 정규화"라며 되살리지 마라. 되살리려면 위 표를 반증하라.

## 표기 충돌 — 반드시 지킬 것

MPC 비용 가중치와 칼만필터 잡음 공분산은 **둘 다 관례적으로 Q, R**이라 불린다.
이 저장소에서는 절대 같은 이름을 쓰지 않는다.

| 대상 | 코드 이름 |
|---|---|
| MPC 상태·입력 가중치 | `W_x`, `W_u`, `W_du` (또는 `Q_ey` 등 명시적 이름) |
| KF 프로세스·측정 잡음 공분산 | `Q_kf`, `R_kf` |

## GP 결합 시

- GP 잔차 평균은 비선형 커널 함수다. 명목 모델이 선형이어도 **결합 모델은
  비선형이 되므로 NMPC**다. QP 솔버(osqp, qpOASES 등)로 전환하려는 시도를 하지 마라.
  전환 가능성은 GP가 없는 명목 케이스에 한해서만 논의 대상이다.
- **결합은 이산(discrete) 형태로 확정되어 있다.** GP 잔차는 상태 차이 단위이므로
  연속 우변에 더하면 `dt_ctrl`배 틀린다. 상세는 `gp-residual.md` 「결합 형태」 참조.

- **GP 평균은 현재 작동점에서 한 번 평가해 지평 상수로 주입한다 (Phase 7 진단 확정).**
  각 지평 스텝의 예측 상태 `z_k` 에서 평가하는 상태의존 결합은 **금지** — mean-only
  MPC 가 GP 부정확 영역을 최적화에서 악용해 불안정해진다(격자 완벽적합에도 -74%).

```
mu_hat = mu_GP(z_now),  z_now = [v_y, gamma, delta_prev]   # solve당 1회, 지평 상수
X[:,k+1] = rk4_step(f_nom, X[:,k], U[k], (vx_k, kappa_k), dt_ctrl) + B_d @ mu_hat
B_d = 4x2, 상단 2x2 단위행렬        # v_y, gamma 행에만 주입
```

- `e_psi`, `e_y` 행에는 **더하지 않는다.** 이 두 행은 순수 기구학이다.
- GP 평가는 solve당 **1회**(작동점)다. 따라서 `M` 은 solve time 에 무관하고 적합
  품질만 결정한다. mu_hat 은 CasADi 파라미터(2)로 주입 -> NLP 재빌드 없음.
- GP 가 KF 를 이기는 이유: 둘 다 지평 상수 외란이지만 GP 는 상태->외란을 직접 학습해
  현재 상태에서 즉시 정확하고, KF 는 시간축 필터라 지연된다 (모델보정자 vs 상태추정기).
- 왜 상태의존이 아닌가: 상태의존 결합 + mean-only 는 최적화기가 GP 부정확 영역을
  악용한다. 이를 쓰려면 caution(분산 페널티)이 필요한데 이번 스코프 밖이다.
- 상태의존 결합의 GP 평가는 RK4 밖 solve당 `N`회였을 것이나, 상수 결합에서는 무의미.

## NLP 구조 재생성 금지

온라인 GP에서 dictionary가 갱신되어도 **NLP를 매 스텝 다시 빌드하지 마라.**
inducing point 개수 `M`을 고정하고, `Z`, `alpha`, 하이퍼파라미터를 CasADi
**파라미터로 주입**해 `nlpsol` 객체를 재사용한다. (제안 — 구조 고정이 목적이며,
실제 solve time 이득은 프로파일링으로 확인할 것)

## 왜 IPOPT 인가 (2026-07-30 정리)

**정직한 답: CasADi 에 번들되어 있고 Mehrez 워크숍 계보를 따랐기 때문이다.**
제어이론적 근거로 고른 것이 아니다. 이 절은 그 사실과, 실제로 재본 대안들을 남긴다.

정당한 근거가 있는 부분은 **"NLP 솔버여야 한다"까지**다 — GP 평균이 비선형 커널이라
결합 모델이 비선형이므로 NMPC 다(위 「GP 결합 시」). 그것이 `osqp`/`qpOASES` 같은 **QP**
솔버를 금지하는 이유이고, "하필 IPOPT"를 정당화하지는 않는다.

**IPOPT 는 실시간 MPC 용 솔버가 아니다.** 범용 내부점법이고, 내부점법의 알려진 약점이
warm start 다. 실시간 NMPC 는 보통 SQP + RTI(스텝당 1반복) 나 active-set QP 를 쓴다.

### 재본 대안 — `fatrop` 은 이 정식화에서 쓸 수 없다 (측정됨)

CasADi 3.7.2 에는 `ipopt` 외에 `fatrop`, `sqpmethod`, `blocksqp`, `qrsqp`, `bonmin`,
`alpaqa` 가 이미 들어 있다(새 의존성 불필요). `fatrop` 은 OCP 의 단계별 구조를 이용하는
내부점법이라 후보였으나, 재보니 못 쓴다.

| 설정 (loop10, 25 s 프로브, N=50) | solve mean | p95 | RMS e_y | 수렴 실패 |
|---|---|---|---|---|
| ipopt 현재 | 12.06 ms | 13.97 | 1.031e-2 | 0 |
| ipopt + warm start | **7.70 ms** | 9.59 | 1.031e-2 | 0 |
| fatrop 기본 | **97.92 ms** | 106.60 | 1.031e-2 | 0 |
| fatrop + `structure_detection: auto` | 70.67 ms | 75.00 | **3.04e+2 발산** | **1250/1250** |

`fatrop` 기본은 답은 맞게 내지만 **10배 느리다**(내부 타이밍: 함수평가 11 ms, 솔버 자체
86 ms — 오버헤드가 아니라 솔버가 느리다). 구조탐지를 켜면 전 스텝 수렴 실패한다.

**원인 추정(미검증)**: `mpc_base.py` 가 `X = opti.variable(4, N+1)` 다음
`U = opti.variable(1, N)` 로 **상태 전체 → 입력 전체** 순서로 변수를 만든다. `fatrop` 이
단계별 구조를 잡으려면 `x0,u0,x1,u1,...` 로 **스테이지별 교차 배치**가 필요하다. 지금
배치로는 구조탐지가 실패해 일반 경로로 떨어지는 것으로 보인다. 확인하려면 변수 순서를
바꿔 다시 재야 한다. **재보지 않고 fatrop 이 빠를 것이라고 적지 마라.**

`acados`(RTI + condensing + codegen)는 이 크기를 보통 1 ms 안에 풀지만
**`requirements.txt` 에 없는 의존성**이다. `python-conventions.md` 「의존성」이 먼저
물어보라고 못박아 뒀고, 솔버 교체는 기존 결과와의 비교 가능성을 깬다. 도입하려면
사용자 승인 + 전 시나리오 재측정이 전제다.

## 지평을 늘릴 때 — 먼저 warm start 를 확인하라 (2026-07-30)

`N` 을 키워 실시간성이 깨졌다면 **정식화를 손대기 전에 솔버 옵션을 먼저 보라.**
move blocking(제어지평 < 예측지평) 같은 정식화 변경은 아래 이유로 여기서는 효과가 적다.

**multiple shooting 에서는 상태가 결정변수의 대부분이다.**

```
N_p=50            X = 4x51 = 204,  U = 50   -> 254 vars
N_p=50, N_c=15    X = 4x51 = 204,  U = 15   -> 219 vars   (고작 -14%)
```

측정된 solve 비용은 변수 수에 대략 선형이므로 균등 move blocking 의 기대 절감은
1~1.5 ms 다. warm start 활성화가 2.5 ms 를 아꼈으므로 **비교가 안 된다.** blocking 이
크게 남으려면 condensing(single shooting)으로 `X` 를 소거해야 하는데, 그건 정식화
재작성이고 조건수가 나빠진다.

**게다가 균등 blocking 은 이 문제에서 「틀린 0」과 같은 부류의 오류를 만든다.** 꼬리
스텝의 `delta` 를 하나로 묶으면 옵티마이저에게 "그 구간 내내 한 조향값으로 충분하다"고
말하는 셈인데, 정상선회에 필요한 `delta` 는 `kappa` 를 따라간다. `N_p=50` 의 꼬리 35
스텝은 `vx=25` 에서 17.5 m 이고 loop10 의 클로소이드 길이가 20 m 이므로 **곡률 전이를
그대로 걸친다.** 꼬리 비용에 없앨 수 없는 성분이 생기고 그 기울기가 지금 적용할 입력을
오염시킨다.

굳이 blocking 을 쓸 거면 **비균등 블록**이어야 한다 — 실제 적용되는 입력은 `k=0` 이므로
앞은 촘촘히, 꼬리는 굵게.

### 측정 — 꼬리 동결(균등)이 굵은 블록보다 **느리고 추종도 나쁘다** (2026-07-30)

loop10 전체 랩, 비선형 플랜트, warm start 켠 상태:

| 설정 | vars | solve mean | p95 | dt 초과 | RMS `e_y` | 실패 |
|---|---|---|---|---|---|---|
| N=50 블로킹 없음 | 254 | 9.19 ms | 12.77 | 0.6% | 7.6630e-3 | 0 |
| **N=50 자유20 + 꼬리 굵은블록** `[1]x20+[4]x5+[10]x1` | 230 | **7.77 ms** | **9.69** | **0.1%** | 7.6641e-3 | 0 |
| N=50 자유20 + **꼬리 동결** `[1]x20+[30]x1` | 225 | 9.17 ms | 15.15 | 1.9% | **7.8110e-3** | 0 |
| N=60 블로킹 없음 | 304 | 10.61 ms | 15.03 | 0.8% | 7.4814e-3 | 0 |

- **굵은 블록은 사실상 공짜다**: 블로킹 없음 대비 solve mean −15%, p95 −24%, RMS `e_y`
  차이는 **+0.014%**(7.6630e-3 -> 7.6641e-3).
- **꼬리 동결은 변수가 더 적은데도(225 < 230) 더 느리다**(mean 9.17 vs 7.77, p95 15.15
  vs 9.69) **그리고 추종도 1.9% 나쁘다**. 변수 수가 아니라 **문제가 어려워진 것**이다 —
  달성 불가능한 꼬리를 강요하면 옵티마이저가 그 타협을 찾느라 더 고생한다. 위에서 예측한
  「틀린 0」과 같은 부류의 오류가 측정으로 확인된 셈이다.
- **`u_blocks` 의 첫 블록 크기는 1 이어야 한다**(`MpcConfig` 검증에서 강제). 플랜트에
  실제로 적용되는 입력은 `u_0` 뿐이고, 그 스텝만은 조향 rate 하드제약을 정확히 지켜야
  한다. `info.U[0, 0]` 이 항상 적용 입력인 것도 이 덕분이다.

### 블로킹의 rate 제약·평활화 항 처리 (구현 규약)

블록 표현은 입력 궤적의 **파라미터화**다. 그래서 두 곳을 `span` 으로 보정한다.
`span = (앞블록 크기 + 뒷블록 크기)/2` = 두 블록 중점 사이의 경과 스텝 수.

- **rate 제약은 블록 경계에서만, 상한은 `drate * span`.** 블록 내부는 차이가 항등적으로
  0 이라 제약을 걸면 자명한 행만 쌓인다. 경계마다 `drate` 로 조이면 꼬리의 도달 가능한
  입력 변화가 블록 크기만큼 줄어(10스텝 블록이면 1/10) 필요한 조향을 표현조차 못 한다.
  실제 액추에이터는 그 시간 동안 연속적으로 움직일 수 있으므로 `drate*span` 이 물리에
  맞는 상한이다. `u_0` 만은 첫 블록 크기가 1 이라 `span=1` -> 정확히 `drate` 다.
- **평활화 항은 `span` 으로 나눈다**: `R_ddelta * (jump)^2 / span`. 원식은 스텝당 차분
  `span` 개의 합인데 블로킹하면 한 번의 점프로 뭉친다. 나누지 않으면 같은 총 변화량에
  대해 penalty 가 `span` 배 과대평가되어(4스텝 블록이면 4배) 평활화 가중이 조용히 세진다.

`u_blocks` 를 비우면 전 스텝이 경계이고 `span=1` 이라 **옛 식과 정확히 같아진다**
(회귀 확인: loop10 RMS `e_y` 7.4814e-03 이 리팩터 전후 소수 5자리까지 동일).

**지평을 늘려도 추종이 좋아진다는 보장은 없다.** 세 경로에서 전부 같은 방향이었다:
`N=30 -> 60` 에서 RMS `e_y` 가 ay4 +3.1%, racetrack +2.2%, loop10 +10.6% **악화**.
IPOPT 반복수는 네 경우 모두 p95 = 5 로 같았으므로 반복이 늘어난 것이 아니라 NLP 크기가
2배라 반복당 비용이 2배다. 지평을 키우는 근거는 추종오차가 아니라 다른 데(제약 예견,
안정성 여유)에서 와야 한다.

## 솔버 운영

- **warm start**: 이전 해를 저장해 다음 스텝 초기추정으로 재사용한다.
  **초기추정을 넣는 것만으로는 절반이다** — IPOPT 기본값이
  `warm_start_init_point: no` 라서 넘겨준 초기점을 경계 안쪽으로 밀어내고 배리어·승수를
  매번 처음부터 잡는다. 즉 초기추정을 만들어 두고 버리게 된다. **다음 네 옵션을 반드시
  함께 켜라** (`configs/mpc/default.yaml`):
  `warm_start_init_point: "yes"` / `warm_start_bound_push: 1e-8` /
  `warm_start_mult_bound_push: 1e-8` / `mu_init: 1e-4`.
  `"yes"` 는 인용부호 필수 — YAML 1.1 은 맨 yes 를 boolean 으로 읽고 IPOPT 는 문자열을
  받는다.

  측정 (loop10 전체 랩, 비선형 플랜트):

  | | solve mean | p95 | max | dt 초과 | IPOPT iter | RMS e_y |
  |---|---|---|---|---|---|---|
  | N=50 끄면 | 11.34 ms | 13.63 | 79.0 | 0.1% | 4.5 | 7.6630e-3 |
  | N=50 켜면 | **8.79 ms** | 14.22 | 62.2 | 0.1% | **2.8** | 7.6630e-3 |
  | N=60 끄면 | 19.13 ms | 25.56 | 112.8 | **35.3%** | 5 | 7.4814e-3 |
  | N=60 켜면 | **10.05 ms** | 15.16 | 78.4 | 0.5% | **2.8** | 7.4814e-3 |

  반복수 -40%, **RMS `e_y` 는 소수 5자리까지 동일**(정확도를 팔아 속도를 산 것이 아니다),
  수렴 실패 0. 이 덕분에 `N=50~60` 이 실시간 안에 들어온다.

  주의 두 가지 — ① warm start 된 내부점법은 active set 이 급변할 때(조향 rate 한계 접촉
  등) 덜 강건할 수 있다. 위 측정에서는 실패 0 이고 max solve 도 안 튀었지만
  `converged`·fallback 경로를 계속 지켜봐라. ② 위 표에서 N=50 끄면(11.34) 대 N=60
  끄면(19.13) 의 차이는 변수 수 증가(1.20배)로 설명되지 않는다. 이 머신의 런 간 변동이
  섞여 있으니 **개별 수치를 과신하지 마라.** 견고한 것은 반복수 4.5~5 -> 2.8 이라는
  메커니즘 수준 결과다.
- **solve time**: 매 호출마다 기록해 반환한다. Part 2의 핵심 지표다.
  IPOPT iteration 수와 수렴 플래그도 함께 반환한다.
- **수렴 실패 처리**: 조용히 넘어가지 마라. 실패를 로그에 기록하고,
  fallback(이전 해의 shift 적용) 여부를 명시적으로 구현한 뒤 그 사실을 보고한다.
  실패율은 결과 리포트에 반드시 포함한다.
- IPOPT 옵션은 config 에서 읽는다. `max_iter`, `tol`, `print_level` 은 `MpcConfig` 의
  이름 있는 필드이고, **그 밖의 옵션은 `ipopt_extra` 로 그대로 통과**한다(옵션마다
  dataclass 필드를 늘리지 않기 위한 통로. 재현성 스냅샷에는 남는다).
  케이스 간 비교 시 옵션을 동일하게 유지하라. 다르면 solve time 비교가 무의미하다.
