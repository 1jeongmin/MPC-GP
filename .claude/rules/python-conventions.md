# 코딩 규약

## 파라미터

- 물리 파라미터·MPC 가중치·솔버 옵션 **하드코딩 절대 금지.** 전부 `configs/`에서 읽는다.
- config는 dataclass(`VehicleConfig`, `MpcConfig`, `GpConfig`, `EkfConfig`, `SimConfig`)로
  로드하고, 로드 시점에 유효성 검사를 한다
  (물리 파라미터 양수, `a+b > 0`, `vx_range` 하한 > 0 등).
- 값에 근거가 없으면 YAML에 `# TODO:` 주석으로 남긴다. 그 주석을 지우지 마라.

## 단위

- 내부는 전부 SI, 각도는 전부 **rad**. deg 변환은 플롯 축에서만.
- 모든 함수 docstring에 인자·반환값의 **단위를 명시**한다. (`rad`, `m/s`, `N/rad`, ...)
- 단위가 섞일 수 있는 변수명에는 접미사를 붙인다 (`delta_rad`, `delta_deg`).

## CasADi ↔ numpy 분리

- 한 함수가 두 경로를 겸하지 않는다. 이름으로 구분한다 (`*_np` / `*_ca` 또는
  모듈 분리). 호출자가 어느 경로인지 헷갈리면 잘못 설계된 것이다.
- CasADi 심볼릭 표현 안에서 numpy 함수를 호출하지 마라 (`np.sin` → `ca.sin`).
- 제어 루프 안에서 PyTorch/GPyTorch를 호출하지 마라. 학습은 오프라인, 추론은
  CasADi로 변환된 표현으로 한다.

## 구조

- 파일 하나에 책임 하나. 300줄을 넘으면 분리를 검토하라.
- 케이스 분기를 `if case == "..."`로 늘리지 마라. 인터페이스 + 주입으로 해결한다.
- 타입힌트를 붙인다. 배열은 shape을 docstring에 적는다 (`(4,)`, `(4, N+1)`).

## 난수·재현성

- 전역 난수 상태에 의존하지 마라. `np.random.default_rng(seed)`를 명시적으로 넘긴다.
- seed는 config에서 읽고 결과와 함께 저장한다.

## 의존성

- `requirements.txt`에 없는 라이브러리를 임의로 추가하지 마라. **먼저 물어라.**
- 특히 최적화 솔버·GP 프레임워크 교체는 실험 결과 비교에 직접 영향을 준다.

## 로깅

- `print` 대신 `logging`을 쓴다. 수치 결과 보고는 예외.
- 예외를 삼키지 마라. `except: pass` 금지. 최소한 로그를 남기고 다시 던진다.

## 주석

- "무엇을"이 아니라 "왜"를 적는다. 특히 부호 규약, 좌표계, 적분기 선택 이유,
  성능 때문에 우회한 부분은 반드시 이유를 남긴다.
- 수식을 구현한 부분에는 대응하는 문서·룰 파일 위치를 적는다
  (예: `# vehicle-model.md 부호 규약 참조`).
